# Cross-site Scripting (XSS)

## Introduction to XSS

- **Abbreviation:** Cross-site Scripting is abbreviated as **XSS** (not CSS, which stands for Cascading Style Sheets).
- **Origin:** Originally called "cross-site" due to early browser security flaws that allowed information from one site to be shared with another.
- **Prevalence:** One of the most common web application vulnerabilities.
- **Exploitation:** Takes advantage of the trust a user's browser has for a legitimate website.
- **Complexity:** Can be complex and varied in its implementation.
- **Primary Language:** XSS commonly uses **JavaScript** because it is a very popular scripting language in browsers, and almost everyone has JavaScript enabled.

## How a Cross-site Scripting Attack Works (High-Level)

- **Actors:**
  - **Attacker:** The malicious party.
  - **Victim:** The user whose data is targeted.
  - **Trusted Website:** A legitimate website that the victim trusts and uses.

### Attack Flow

1. **Attacker sends a malicious link:** The attacker sends a link containing a malicious script to the victim, often via email, text message, or social media.
2. **Victim clicks the link:** When the victim clicks on the link, it appears to lead to a legitimate website but is actually embedding a malicious script in the browser's context.
3. **Legitimate site loads with malicious script:** The trusted website loads in the victim's browser. Due to a vulnerability on the website, the malicious script provided by the attacker is executed within the context of the trusted website.
4. **Malicious script sends data to attacker:** The executed malicious script then sends the victim's private data (e.g., session cookies, credentials) directly to the attacker.

### Key Concept: 
The browser executes the malicious script because it believes the script originated from the trusted website, thus granting it access to the trusted site's resources and the victim's session data.

## Types of XSS Attacks

### 1. Non-persistent (reflected) XSS Attack
- **Description:** The website allows scripts to run based on user input, which is immediately reflected back to the user without being stored.
- **Common Source:** Search boxes are a common source of this vulnerability.
- **Mechanism:**
  - The attacker crafts a URL that includes a malicious script within a parameter (e.g., a search query).
  - The attacker emails this crafted link to the victim.
  - When the victim clicks the link, the vulnerable website takes the malicious script from the URL parameter and "reflects" it back into the HTML response, which is then executed by the victim's browser.

- **Execution Context:** The script embedded in the URL executes as if it came from the legitimate server.
- **Goal:** To run a script that sends credentials, session IDs, or cookies from the victim's browser to the attacker.
- **Impact:** Steals information without the user knowing (very sneaky).
- **Example (Shopping Cart):**
  - A shopping cart website has a credit card number field that doesn't validate input.
  - An attacker could craft a script: `"></script><script>alert("Your session information" + document.cookie)</script>`
  - If this script is entered into the credit card field and the "Purchase" button is clicked, an alert box appears showing the session ID (the real attack would send this to the attacker).
  - The attacker might embed this malicious code in a link that the victim clicks, leading them to the vulnerable page where their browser executes the injected script.

### 2. Persistent (stored) XSS Attack
- **Description:** The attacker posts a message containing a malicious payload (script) to a social network, forum, or any website where user input is stored and later displayed to other users.
- **Persistence:** The malicious script is "persistent" because it is stored on the vulnerable server.
- **No Specific Target:** Unlike reflected XSS, there's no single target. Everyone who views the page containing the stored malicious message will have the payload executed in their browser.
- **Spread:** This type of attack can spread very quickly on social networking sites.
  - Anyone who views the message can have the malicious code executed.
  - The malicious code itself might be designed to automatically post or propagate itself to other users' feeds, further spreading the attack.

## Real-world Example: Hacking a Subaru (June 2017)

- **Security Researcher:** Aaron Guzman
- **Vulnerabilities Found:**
  - **Non-expiring Tokens:** When authenticating with the Subaru website to manage vehicle features, users received a token that never expired. This is a significant security flaw because tokens should have a limited lifespan.
  - **Broad Token Permissions:** A valid token allowed any service request, including adding an email address to someone else's account. This meant an attacker with a token could gain full access to someone else's car controls.
  - **XSS Vulnerability in Web Front-end:** The Subaru web front-end included an XSS vulnerability.

- **Attacker Strategy:**
  An attacker could get the user to click a malicious link, which would trigger the execution of the malicious script. This allowed the attacker to gain full control over the user's vehicle management features simply by getting the user to click a single link.

## Exam Takeaways

1. **Define XSS and its Abbreviation:**
   - Cross-site Scripting (XSS) is a web security vulnerability that enables attackers to inject client-side scripts into web pages viewed by other users.
   - Abbreviated as XSS to avoid confusion with CSS (Cascading Style Sheets).

2. **Explain the Core Mechanism of XSS:**
   - XSS exploits the browser's trust in a website.
   - An attacker injects malicious client-side script (typically JavaScript) into a web page.
   - When a victim's browser loads the page, it executes the malicious script as if it were legitimate content from the trusted site.
   - This allows the script to access and steal sensitive data (like session cookies, credentials) from the victim's browser, or perform actions on the user's behalf.

3. **Differentiate Between Non-persistent (Reflected) and Persistent (Stored) XSS:**
   - **Non-persistent (Reflected) XSS:**
     - **Delivery:** Malicious script is delivered via a crafted URL (e.g., in a search query parameter).
     - **Execution:** The vulnerable server reflects the script back to the user's browser, where it executes immediately.
     - **Persistence:** The script is not stored on the server; it's a one-time execution per click.
     - **Target:** Primarily targets individual users who click the malicious link.

   - **Persistent (Stored) XSS:**
     - **Delivery:** Malicious script is stored on the vulnerable server (e.g., in a database, comment section, social media post).
     - **Execution:** Any user who views the affected page will have the malicious script execute in their browser.
     - **Persistence:** The script remains on the server, affecting multiple users over time.
     - **Target:** Affects all viewers of the compromised content.

4. **Identify Common Impacts/Goals of XSS Attacks:**
   - **Session Hijacking:** Stealing session cookies to impersonate the user.
   - **Credential Theft:** Stealing login credentials.
   - **Defacement:** Altering the appearance or content of a website.
   - **Malware Distribution:** Redirecting users to malicious sites or downloading malware.
   - **Phishing:** Displaying fake login forms to trick users.

5. **Describe Protection Strategies for XSS:**
   - **For Users:**
     - **Be wary of untrusted links:** Never click suspicious links; manually type URLs.
     - **Keep software updated:** Patch browsers and applications regularly.
     - **(Limited) JavaScript control:** Consider disabling JavaScript or using browser extensions to control its execution on untrusted sites.

   - **For Developers:**
     - **Input Validation:** Strictly validate and sanitize all user input to remove or neutralize malicious code before it's processed or stored.
     - **Output Encoding:** Encode all output that includes user-supplied data before rendering it in the browser, ensuring it is displayed as text rather than executable code.

6. **Recall the Subaru Hacking Example:**
   - Understand how a combination of vulnerabilities (non-expiring tokens, broad token permissions, and XSS) allowed an attacker to gain full control over a user's vehicle management features simply by getting the user to click a malicious link. This highlights the severe real-world consequences of XSS when combined with other flaws.
