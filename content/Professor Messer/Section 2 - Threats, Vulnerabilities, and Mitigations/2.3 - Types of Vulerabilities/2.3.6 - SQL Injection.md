# 2.1.1 SQL Injection

## Introduction to Code Injection

- **Code Injection Defined:** Adding your own information (code) into a data stream.
- **Enabling Factor:** Poor programming practices that fail to properly handle input and output, allowing unexpected data to be interpreted as code.
- **Purpose:** To inject unnecessary or unwanted application data.
- **Common Data Types Vulnerable:**
    - HTML
    - SQL (Focus of this video)
    - XML
    - LDAP
    - etc.

## SQL Injection

### What is SQL?

- **SQL:** Structured Query Language.
    - The most common language used for managing and querying relational databases.
    - Used by applications to interact with databases.

### SQL Injection (SQLi)

- **SQL Injection (SQLi):**
    - An attacker inserts their own SQL requests into an existing application’s query.
    - The application should not allow this, but vulnerabilities exist due to inadequate input validation.
    - **Ease of Execution:** Often executed directly in a web browser by injecting malicious code into form fields (e.g., username, password, search boxes).

## Building a SQL Injection

### Example Website Code

```sql
"SELECT * FROM users WHERE name = '" + userName + "'";
```

- `userName` is the variable where user input is placed.

#### Normal Scenario

- **User Inputs:** `Professor`
- **SQL Database Receives:**
    ```sql
    SELECT * FROM users WHERE name = 'Professor';
    ```
- **Result:** Returns data for the user named 'Professor'.

#### SQL Injection Scenario (Bypassing Authentication)

- **Attacker Inputs:** `Professor' OR '1'='1`
- **SQL Database Receives:**
    ```sql
    SELECT * FROM users WHERE name = 'Professor' OR '1'='1';
    ```
    - **Explanation of Injected Code:**
        - `'` (single quote): Closes the string for the `name` field.
        - `OR '1'='1'`: An `OR` condition is added. `'1'='1'` is always true.
        - `--` (or `;` or `/*`): These are often used to comment out or terminate the rest of the original query, preventing syntax errors. (Professor uses `''` to close the string, which works too).
    - **Result:** Because `'1'='1'` is always true, the `WHERE` clause evaluates to true for every row in the `users` table.
    - **Impact:** The query returns all information from the `users` table, not just for 'Professor'.

### Severity of SQLi

- **View All Database Information:** Complete data breach (confidentiality).
- **Delete Database Information:** Data loss (availability) or corruption (integrity).
- **Add Users:** Unauthorized access, privilege escalation (integrity).
- **Denial of Service (DoS):** Bringing down the database server or making it unresponsive (availability).
- Gives the attacker significant control over the database.
- No specialized software is required; simple text input is enough.

## SQL Injection Demonstration

### Application Used: WebGoat

### Scenario

- **Employee Lookup Form:** Requires "Employee Name" and "Authentication TAN".
- **Normal Query:**
    - Input: `Employee Name: Smith`, `Authentication TAN: 3SL99A`
    - Result: Returns a single record for "John Smith" (USERID, FIRST_NAME, LAST_NAME, DEPARTMENT, SALARY, AUTH_TAN). The query is limited to these specific credentials.
- **Injected Query:**
    - Input: `Employee Name: Smith`, `Authentication TAN: 3SL99A' or '1'='1`
    - Result: Returns all employee records from the database (Paulina Travers, Abraham Holman, John Smith, Tobi Barnett, Bob Franco, etc.).
    - **Success Message:** "You have succeeded! You successfully compromised the confidentiality of data by viewing internal information that you should not have access to. Well done!"
- This demonstrates how `OR '1'='1'` bypasses intended security logic and retrieves unauthorized data.

## Takeaways for Exam Preparation

### Core Concepts

1. **Code Injection:** Understand the general concept of code injection as adding unauthorized data or code into an application's data stream, exploiting poor input/output handling.
2. **SQL Definition:** Know that SQL is the language used to manage and query relational databases.
3. **SQL Injection (SQLi):** This is a specific type of code injection where an attacker manipulates SQL queries by injecting malicious SQL code into input fields.

### How SQLi Works

1. **Vulnerability Root Cause:** SQLi occurs due to *improper input validation* by the application. The application directly concatenates user input into SQL queries without sanitizing or escaping special characters.
2. **Query Manipulation:** Attackers use SQL syntax (like single quotes `'`, `OR`, `AND`, comments `--` or `/* */`, semicolons `;`) to alter the original intent of the database query.
3. **Bypass Logic:** The classic `OR '1'='1'` technique forces the `WHERE` clause to always evaluate to `TRUE`, effectively returning all records from a table, regardless of the initial conditions.

### Impact and Consequences

1. **Confidentiality Breach:** Unauthorized viewing of sensitive data (e.g., user lists, financial records, personal information). This is the most common immediate outcome of a successful SQLi.
2. **Integrity Breach:** Unauthorized modification or deletion of data, or adding new, illegitimate users/records.
3. **Availability Breach (DoS):** Malicious queries can crash the database or slow it down significantly, leading to a denial of service.
4. **Complete Database Control:** In severe cases, attackers can gain full control over the database, allowing them to execute arbitrary commands on the database server.

### Practical Aspects

1. **Ease of Exploitation:** SQLi can often be executed with minimal technical skill directly through standard web browser input fields (e.g., login forms, search bars). No specialized tools are strictly required for basic exploits.
2. **Common Exploit String:** Remember the `' OR '1'='1` pattern as a common and effective SQLi payload for bypassing authentication or retrieving all records.

### Prevention

- **Input Validation/Sanitization:** All user input must be rigorously validated and sanitized to remove or neutralize any potentially malicious characters before being used in SQL queries.
- **Parameterized Queries (Prepared Statements):** This is the *most effective defense*. Instead of concatenating user input directly, parameterized queries separate the SQL code from the user-provided data, ensuring that input is always treated as data, not executable code.
