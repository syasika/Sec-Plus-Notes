# Cryptographic Attacks

## Introduction
- **Core Question:** If data is encrypted and sent, is it truly secure? How do we know?
- **Attacker's Goal:** Not to find the encryption key directly but to "break the safe" (the cryptography itself).
- **Focus of Attacks:**
  - Finding ways to **undo the security** of cryptographic algorithms.
  - Exploiting **cryptographic shortcomings** (weaknesses in the algorithm or protocol).
  - The problem is often the **implementation** of cryptography, rather than the algorithm design itself.
- **Importance of Public Algorithms:** Cryptographic protocols and algorithms are often made public so that everyone can examine them for weaknesses. If a weakness is found, the algorithm is deprecated. Therefore, algorithms in use today have generally withstood scrutiny.

## Birthday Attack
- **Analogy:** Birthday Paradox
  - In a classroom of **23 students**, there's about a **50% chance** of two students sharing a birthday.
  - In a class of **30 students**, the chance increases to about **70%**.
  - This is about *any* two students sharing a birthday, not a specific student sharing with anyone else.
- **Digital World Equivalent:** **Hash Collision**
  - **Definition:** A hash collision occurs when two different plaintexts produce the exact same hash value (digest).
  - Attackers use brute force to find these collisions by generating multiple versions of plaintext and computing their hashes, looking for matches.
- **Protection:** Use a **large hash output size**. The larger the hash, the more difficult it is to find a collision.

## Collisions: MD5 Example
- **Ideal Hash Digest Property:** Hash digests are supposed to be **unique**. Different input data should *never* create the same hash.
- **MD5 (Message Digest Algorithm 5):**
  - First published in **April 1992**.
  - **Collisions identified in 1996**. This was a significant vulnerability.
  - **Real-world Impact (December 2008):** Researchers successfully created a rogue Certificate Authority (CA) certificate that appeared legitimate when checked with MD5.
    - They used this vulnerability to build other certificates that seemed legitimate, issued by RapidSSL, effectively undermining trust in MD5-based digital signatures.
  - **Industry Response:** MD5 was quickly deprecated and is no longer considered secure for cryptographic hashing due to its susceptibility to collisions.

## Downgrade Attack
- **Concept:** Instead of using perfectly good encryption, an attacker forces systems to use something that's **not so great** (i.e., less secure or unencrypted).
- **Mechanism:** Force systems to **downgrade their security** during protocol negotiation.
- **Reason:** Often exploits **implementation flaws** in how systems negotiate encryption protocols, rather than flaws in the encryption algorithms themselves.
- **Example:** **SSL Stripping**

## SSL Stripping
- **Nature of Attack:** Combines an **on-path attack** (Man-in-the-Middle) with a **downgrade attack**.
- **Implementation:** Difficult to set up but offers significant returns for the attacker.
- **Attacker's Position:** The attacker must sit in the middle of the conversation between the victim and the web server.
- **Victim's Perception:** The victim's browser page isn't encrypted (the 'S' is stripped away from HTTPS).
- **Attack Flow Diagram:**
  1. **Victim requests `http://example.com`** (unencrypted HTTP).
  2. **Attacker intercepts** this request.
  3. **Attacker passes `GET http://example.com` to Web Server**.
  4. **Web Server responds `301 Moved`** (redirecting to `https://example.com`) to the attacker.
  5. **Attacker intercepts the `301 Moved` response** and *does not* pass it to the victim.
  6. **Attacker initiates a *new*, secure connection to the Web Server:** `GET https://example.com`.
  7. **Web Server responds `200 OK (HTTPS)`** to the attacker (thinking it's a legitimate secure request).
  8. **Attacker sends `200 OK (HTTP)` to the Victim**, rewriting any HTTPS links on the page back to HTTP.
  9. **Victim attempts to log in:** `POST http://example.com` with `user: professor & password: ninja1` (sent unencrypted over HTTP).
  10. **Attacker intercepts these cleartext credentials**.
  11. **Attacker initiates a *new*, secure POST request to the Web Server:** `POST https://example.com` with the *stolen credentials*.
  12. **Web Server responds `200 OK (HTTPS)`** to the attacker (successful login).
  13. **Attacker sends `200 OK (HTTP)` to the Victim** (confirming login).
- **Result:** All subsequent communication between the victim and the attacker occurs over unencrypted HTTP, allowing the attacker to view and potentially modify all data. The attacker maintains a secure HTTPS connection with the web server, acting as a transparent proxy.

# Exam Takeaways
1.  **Cryptographic Attacks Target:**
    - **Algorithm Flaws:** Weaknesses in the mathematical design of cryptography (e.g., MD5 collisions).
    - **Implementation Flaws:** Weaknesses in how the algorithm is put into practice (e.g., SSL stripping).
    - **Key Takeaway:** Even strong algorithms can be compromised by poor implementation.

2.  **Birthday Attack / Hash Collisions:**
    - **Concept:** Exploits probability to find two different inputs that produce the same hash output.
    - **Impact:** Can undermine data integrity (e.g., digital signatures where different documents appear to be the same).
    - **Mitigation:** Use hash algorithms with sufficiently **large output sizes** (e.g., SHA-256 or SHA-3, not MD5).

3.  **MD5 as a Cautionary Tale:**
    - MD5 is a prime example of a hash algorithm that was once considered strong but became vulnerable to **collision attacks**.
    - The 2008 CA certificate exploit demonstrated a **critical real-world impact**, leading to its widespread deprecation for security-sensitive applications.
    - **Key Takeaway:** Always use current, strong, and well-vetted cryptographic primitives.

4.  **Downgrade Attacks:**
    - **Concept:** Forces a communication system to use a weaker, less secure, or unencrypted protocol version.
    - **Mechanism:** Often involves tricking one or both parties into believing a secure connection isn't possible or necessary.
    - **Key Takeaway:** Configure systems to only allow strong, current cryptographic protocols and disable older, weaker ones.

5.  **SSL Stripping (a type of Downgrade Attack):**
    - **Mechanism:** An **on-path attacker** intercepts initial HTTP requests, prevents redirects to HTTPS, and then acts as a proxy:
        - Communicates securely (HTTPS) with the legitimate web server.
        - Communicates insecurely (HTTP) with the victim's browser.
    - **Impact:** All data exchanged between the victim and the attacker (including credentials) is in **cleartext**, making it vulnerable to eavesdropping and manipulation.
    - **Key Takeaway:** Users should always verify that their browser shows a secure HTTPS connection (padlock icon) before entering sensitive information. Implement HSTS (HTTP Strict Transport Security) on web servers to mitigate this by forcing browsers to only use HTTPS.
