# 1. Hashes

## Definition
A cryptographic hash represents data as a short, fixed-length string of text. Also known as a **message digest** or a **fingerprint**.

### Key Properties
- **One-way Function:** It's impossible to recover the original message/data from the hash.
  - *Crucial Distinction:* Unlike encryption, which is a two-way process (encrypt and decrypt), hashing is one-way.
- **Fixed-size Output:** Regardless of input size, the output hash will always be the same length for a given algorithm.
- **Unique Output:** Different inputs should ideally produce different hashes.
- **Avalanche Effect:** Even a minor change in the input data results in a drastically different hash output.

### Practical Uses
- **Storing Passwords / Confidentiality:** Instead of storing actual passwords (even encrypted ones, which could be decrypted), systems store a hash of the password. During login, the user's entered password is hashed and compared to the stored hash. If they match, authentication succeeds.
  - This means nobody (not even administrators) knows your actual password.
- **Verifying Data Integrity:** To ensure a downloaded document or file is the same as the original, a hash is provided by the source. You calculate the hash of your downloaded file and compare it to the source's posted hash. If they match, the file’s integrity is confirmed (it hasn't been tampered with).
- **Digital Signatures:** Hashes are fundamental in creating digital signatures.

### Example: SHA256
**SHA256:** A common hashing algorithm that produces a 256-bit hash represented as 64 hexadecimal characters.

#### Demonstration of Avalanche Effect:
- Input 1: "My name is Professor Messer."
  - SHA256 Hash: `19da9a2e26f3bff67f0522f962851c42542b8659333ac53397c8d65aa7a3f871`
- Input 2: "My name is Professor Messer!" (only a period changed to an exclamation mark)
  - SHA256 Hash: `54381cae1eea10892d81c8688d06d1928b4ee8495061a792864f83092b033aea`
- *Observation:* A single character change leads to a completely different hash, making it impossible to guess input changes from output changes.

## 2. Collisions

### Definition
A **collision** occurs when two different inputs produce the exact same hash output.

### Ideal Hash Function
An ideal hash function should be computationally infeasible to find collisions. Different inputs should *never* create the same hash in practical use.

### MD5 Collision Problem
The **MD5** hashing algorithm was found to have collision problems in 1996, making it possible to find two different inputs that generate the same MD5 hash relatively easily.
- **Recommendation:** Do not use MD5 for anything important where collision resistance is critical (e.g., integrity checks, digital signatures).
- *Visual Example:* Two slightly different binary inputs (highlighted in red) fed into MD5 produce identical hashes. This demonstrates a practical collision.

## 3. Adding Salt to Passwords

### Problem
Without salting, if two users have the same password, their stored password hashes would be identical, making **Rainbow Tables** effective.

### Salt Definition
Random data added to a password *before* hashing.
- **Uniqueness:** Every user gets their own random salt.
- **Storage:** The salt is commonly stored alongside the password hash in the database.

### Benefits of Salting
- **Defeats Rainbow Tables:** Because salt randomizes the hash for each user, even if they use the same password, their hashes will be different, rendering rainbow tables ineffective.
- **Slows Down Brute-Force Attacks:** An attacker trying to brute-force passwords would need to test each possible combination of a password and its corresponding salt. This makes brute-forcing much more computationally intensive.

### Example
- Original Password: "password123"
- Salt: "random_salt_string"
- Combined Hashed Value: SHA256("password123random_salt_string")

## 4. Digital Signatures

### Definition
A digital signature provides **Integrity**, **Authentication**, and **Non-repudiation** for electronic documents.

### Security Principles Provided
- **Integrity:** Proves the message was not changed after it was signed.
- **Authentication:** Proves the source of the message (who sent it).
- **Non-repudiation:** Prevents the sender from falsely denying that they sent the message.

### Mechanism (Asymmetric Cryptography)
- **Signing:** The sender uses their **private key** to sign the message. Only the owner of the private key can create this signature.
  - *Important:* The message itself does not need to be encrypted for signing.
- **Verification:** The recipient uses the sender's **public key** to verify the signature. If the public key successfully verifies the signature, it confirms the private key was used to sign it. Any change in the message (even a single character) will invalidate the signature.

### Example: Creating and Verifying a Digital Signature
1. **Original Message (Plaintext):** Alice has a message for Bob: "You're hired, Bob."
2. **Hash Generation:** Alice's computer calculates a hash of the plaintext message using a hashing algorithm.
3. **Signature Creation:** Alice's computer encrypts the generated hash using Alice's private key. This encrypted hash is the digital signature.
4. **Transmission:** Alice sends the original plaintext message along with the digital signature (often as an attachment or appended to the message) to Bob.

### Example: Verifying a Digital Signature
1. **Receive Message:** Bob receives the plaintext message and the digital signature from Alice.
2. **Decrypt Signature:** Bob's computer decrypts the digital signature using Alice's public key. The result of this decryption is the hash that Alice originally generated.
3. **Hash Received Message:** Bob's computer independently calculates a hash of the *received plaintext message* using the *same hashing algorithm* Alice used.
4. **Comparison:** Bob's computer compares the hash obtained from decrypting the signature with the hash generated from the received plaintext.
5. **Result:**
  - **If hashes match:** The digital signature is valid. Bob knows:
    - The message hasn't been altered (Integrity).
    - The message truly came from Alice (Authentication).
    - Alice cannot deny sending the message (Non-repudiation).
  - **If hashes do not match:** The digital signature is invalid, indicating either that the message was tampered with in transit or that the signature was created by someone other than Alice.

# Takeaways for Exam

1. **Define Hashing:** A one-way mathematical function that converts data of any size into a fixed-length string (message digest/fingerprint). It is *not* encryption because it cannot be reversed.
2. **Properties of a Cryptographic Hash Function:**
   - **Fixed Output Size:** Output is always the same length.
   - **One-Way:** Computationally infeasible to reverse.
   - **Collision Resistance:** Extremely difficult to find two different inputs that produce the same hash.
   - **Avalanche Effect:** Small input change results in a large output change.
3. **Key Hash Algorithms to Know:**
   - **SHA256:** A strong, commonly used algorithm (256-bit output).
   - **MD5:** A weak algorithm with known collision vulnerabilities since 1996. Do NOT use for security-sensitive applications.
4. **Understanding Collisions:** When two different inputs yield the same hash output. A major weakness in a hash function.
5. **Practical Uses of Hashing:**
   - **File Integrity:** Verifying that a downloaded file has not been altered by comparing its hash to a trusted source's hash.
   - **Password Storage:** Storing hashes of passwords (rather than plaintext or encrypted passwords) to protect user credentials.
6. **Salting Passwords:**
   - **Purpose:** To prevent **Rainbow Tables** attacks and slow down brute-force attacks.
   - **Mechanism:** Random, unique data (salt) is added to each user's password *before* hashing. The salt is stored with the hash.
   - **Impact:** Even if two users have the same password, their salted hashes will be different, making pre-computed attack tables useless.
7. **Digital Signatures:**
   - **Purpose:** To provide **Integrity**, **Authentication**, and **Non-repudiation** for digital documents.
   - **Process (Asymmetric Cryptography):**
     - **Signing:** Sender hashes the message, then encrypts the hash with their private key. This encrypted hash is the digital signature.
     - **Verification:** Recipient decrypts the digital signature with the sender's public key to retrieve the original hash. They then independently hash the received message and compare the two hashes.
   - **Key Relationship:** The private key is used for *signing*, and the public key is used for *verifying* (this is the opposite of encryption, where the public key encrypts and the private key decrypts).
   - **Message State:** The original message remains in plaintext; only its hash is signed.
