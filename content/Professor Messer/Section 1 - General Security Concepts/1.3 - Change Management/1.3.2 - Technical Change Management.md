## Introduction

- **Putting Change Management into Action**: This section focuses on the technical execution of a Change Management Process plan. It highlights the roles involved and the complexity of upgrades in different environments.

### Complexity of Upgrades
- **Simple vs. Complex Scenarios**:
  - In personal settings, upgrades can be simple with only one or two devices.
  - Enterprise environments often have many interconnected devices (tens to thousands), requiring complex planning and multiple steps for a single upgrade.
  
- **Roles in Change Management**:
  - **Change Management Process (Management/Leadership)**: Focuses on what changes are needed.
  - **Technical Team**: Concerned with how the changes will be implemented.

## Allow List / Deny List (Application Control)

### Purpose
- **Purpose of Application Control**: To mitigate risks such as vulnerabilities, trojan horses, and malware by controlling which applications can execute in an environment.

### Allow List (Whitelist)
- **Definition**: Only applications explicitly approved on the list are permitted to run.
- **Characteristics**: Very restrictive. Default is denial.

### Deny List (Blacklist)
- **Definition**: Applications explicitly named on the list are prevented from running.
- **Characteristics**: More flexible than an allow list. Default is permission.
- **Example**: Anti-virus and anti-malware software often use deny lists to block known malicious code.

## Restricted Activities (Scope of Change)

### Importance of Scope
- Each change control submission has a clearly defined scope that dictates exactly which components and activities are covered.

### Specific Approval
- A change approval is not a blanket permission for any alteration; it's specific to the documented change, such as upgrading printer drivers for 2 hours.

### Scope Expansion during Change Window
- A well-documented change control process defines procedures for expanding the scope if necessary. This ensures proper authorization and minimizes risks from ad-hoc changes.

## Downtime

### Inevitability of Unavailability
- **Service Downtime**: Changes can be disruptive, leading to service unavailability.
  
### Scheduling
- Typically scheduled during non-production hours (e.g., overnight, weekends) to minimize user impact.

### Preventing Downtime (24/7 Operations)
- Strategy: Switch users to a secondary system before upgrading the primary system. After the upgrade, switch back seamlessly.

### Minimizing Downtime Events
- **Automation**: The change process should be as automated as possible for speed and consistency.
- **Backout Plan**: Crucial for minimizing risk. Define procedures for reverting if issues appear during the upgrade.

## Restarts

### Common Requirement
- Restarts are often necessary to fully implement new configuration changes.

### Types of Restarts
- **Reboot the Operating System**
- **Power Cycle the Switch**
- **Bounce the Service**

### Power Outage Recovery Test
- Performing a restart helps confirm the system can recover from a power outage properly.

### Services and Applications
- Stopping and restarting services or daemons (Linux term) can be quick.
- Users may need to close and relaunch applications for new configurations.

## Legacy Applications

### Definition and Characteristics
- **Legacy Applications**: Long-running applications without current support or documentation.
  - **No Longer Supported by the Developer**.
  - **Fear of the Unknown** among IT staff due to lack of documentation.
  - **Quirky Behavior** or unique operational requirements.

### Management Strategy
- **Document the System**: Overcome fear and bring these apps into a supportable cycle.
- **Become the Expert**: Documenting the application helps become an in-house expert.
- **Specific Processes**: Create specific processes for managing quirky applications.

## Dependencies

### Interconnectedness
- One change may depend on another, such as services requiring active services or specific library versions.

### Management Challenge
- Modifying one component can necessitate changing several other dependent components. This complexity needs to be managed carefully.

### Cross-System Dependencies
- Dependencies are not always confined to a single system; they might involve multiple systems or layers (e.g., application, OS, network device).

## Documentation

### Challenges and Requirement
- Keeping documentation up-to-date is difficult due to constant changes.
  - **Outdated Documentation**: A significant risk in IT operations.

### Types of Updates
- **Updating Diagrams and Charts**: Reflect changes to network configurations, IP addresses, etc.
- **Updating Policies and Procedures**: Adding new systems or implementing new technologies may require new operational procedures.

## Version Control

### Purpose
- To track changes to files or configuration data over time.
  
### Benefits
- Allows for easy reversion if issues arise after a change.

### Examples of Version Control Opportunities
- Router configurations, Windows OS patches, application registry entries.

### Implementation
- Some devices/operating systems have built-in version control features.
- Others may require additional management software (e.g., Git, SVN).

## Exam Takeaways

As a student preparing for an exam like CompTIA A+, focus on understanding the *why* and *how* of technical change management rather than just memorizing terms.

1. **Change Management is a Process, Execution is Key**:
   - Understand that while change management defines what changes are needed, the technical team is responsible for how those changes are implemented.
   - Recognize that even "simple" changes can be complex in large enterprise environments due to numerous interconnected components.

2. **Application Control (Allow/Deny Lists)**:
   - **Core Concept**: These lists are fundamental security policies for controlling application execution.
   - **Distinguish**:
     - **Allow List**: Default deny, only approved apps run (very restrictive).
     - **Deny List**: Default allow, only specified bad apps are blocked (less restrictive, often used by anti-malware).
   - **Application**: Be able to identify scenarios where one might be preferred over the other.

3. **Scope and Restricted Activities**:
   - **Key Principle**: Every change approval has a specific, documented scope.
   - **Implication**: An approval for one change does not grant permission for unrelated changes.
   - **Flexibility**: Understand that procedures for expanding the scope during a change window should be predefined within the change management process.

4. **Downtime Management**:
   - **Expectation**: Recognize that technical changes often lead to service downtime.
   - **Mitigation**:
     - Scheduling: Prefer non-production hours.
     - Prevention (24/7): Know the strategy of switching to a secondary system, upgrading the primary system, then switching back to avoid user impact.
     - Backout Plan: Always have a plan to revert to a previous stable state if the change fails. It should be part of the change control documentation.
     - Communication: Users need to be informed of potential outages via emails or change control calendars.

5. **Restarts for Configuration Implementation**:
   - **Necessity**: Restarts are a common way to implement new configuration changes.
   - **Levels**: Understand the different levels: rebooting the entire OS, power cycling hardware, or simply stopping/restarting a specific service/daemon.
   - **Hidden Benefit**: A planned restart during change control acts as a test of the system's ability to recover from a power outage.

6. **Challenges with Legacy Applications**:
   - **Identify**: Recognize the characteristics of legacy applications: old, often undocumented, and potentially unsupported by original developers.
   - **Risk**: They represent a fear of the unknown and can cause quirky behavior.
   - **Best Practice**: Proactive documentation is key to making these systems manageable and bringing them into the organization's support cycle.

7. **Understanding Dependencies**:
   - **Interdependence**: Acknowledge that systems and services are rarely isolated; changes to one component often depend on or affect others.
   - **Complexity**: Be aware that dependencies can exist across multiple systems or different layers of infrastructure.
   - **Planning**: Understanding dependencies is crucial for planning the correct order of operations in a change.

8. **Importance of Documentation**:
   - **Continuous Process**: Documentation is not a one-time task but an ongoing requirement.
   - **Risk**: Outdated documentation is a significant risk in IT operations.
   - **Types**: Understand the need to update network diagrams, configurations, and operational policies with every significant change.

9. **Leveraging Version Control**:
   - **Purpose**: Version control is essential for tracking all modifications to files and configuration data.
   - **Benefit**: Enables easy reversion (rollback) if a change introduces problems.
   - **Application**: Be familiar with opportunities to use version control for various components like router configurations, OS patches, and application settings.
