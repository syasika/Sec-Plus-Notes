# Cloud Infrastructures

## Shared Responsibility Model

### Core Concept
In cloud computing, security responsibility is shared between the cloud provider and the customer. The exact division depends on the **cloud service model** used (IaaS, PaaS, SaaS) and contractual agreements.

### Documentation is Key
Security responsibilities should be clearly documented. Most cloud providers offer a **matrix of responsibilities** to clarify who manages what.

### Variability
Responsibilities can differ between various cloud providers, and contractual agreements can modify the standard responsibility matrix.

#### Responsibility Matrix Example (General)

| Component                         | SaaS (Software as a Service) | PaaS (Platform as a Service) | IaaS (Infrastructure as a Service) | On-Prem (On-Premises) |
| :-------------------------------- | :--------------------------- | :--------------------------- | :--------------------------------- | :-------------------- |
| **Information and Data**          | Customer Managed             | Customer Managed             | Customer Managed                   | Customer Managed      |
| **Devices (Mobile and PCs)**      | Customer Managed             | Customer Managed             | Customer Managed                   | Customer Managed      |
| **Accounts and Identities**       | Customer Managed (partially) | Customer Managed (partially) | Customer Managed                   | Customer Managed      |
| **Identity and Directory Infra**  | Provider Managed (partially) | Provider Managed (partially) | Customer Managed                   | Customer Managed      |
| **Applications**                  | Provider Managed             | Customer Managed (partially) | Customer Managed                   | Customer Managed      |
| **Network Controls**              | Provider Managed             | Customer Managed (partially) | Customer Managed                   | Customer Managed      |
| **Operating Systems**             | Provider Managed             | Provider Managed             | Customer Managed                   | Customer Managed      |
| **Physical Hosts**                | Provider Managed             | Provider Managed             | Provider Managed                   | Customer Managed      |
| **Physical Network**              | Provider Managed             | Provider Managed             | Provider Managed                   | Customer Managed      |
| **Physical Datacenter**           | Provider Managed             | Provider Managed             | Provider Managed                   | Customer Managed      |

### Legend
- **Blue:** Customer Managed
- **Yellow:** Provider Managed
- **Split (Blue/Yellow):** Shared Responsibility

### Observations from Matrix
As you move from **On-Prem** to **IaaS**, **PaaS**, and then **SaaS**, the amount of responsibility managed by the **Cloud Provider (Yellow)** significantly increases. Conversely, the customer's (blue) responsibility decreases. 
- In **SaaS**, customers are primarily responsible for their data, devices, and aspects of user accounts.
- In **IaaS**, more control is shifted to the customer, who manages operating systems, applications, and network controls, while the provider handles the underlying physical infrastructure.

## Hybrid Considerations

### Definition
A **Hybrid Cloud** involves using more than one public or private cloud infrastructure, often integrating them. This approach offers flexibility but introduces additional complexity, especially for security.

### Network Protection Mismatches
- Cloud providers don't always directly communicate or have standardized security configurations between them.
- Requires manual configuration of:
  - **Authentication**: Different identity providers.
  - **Firewall configurations**: Rules may differ, leading to gaps or conflicts.
  - **Server settings**: OS hardening and patch management might vary.

### Different Security Monitoring
Each cloud provider has its own logging formats, terminology, and monitoring tools. Aggregating and analyzing diverse, cloud-specific logs for a unified security posture is challenging.

### Data Leakage Risks
Data often needs to be transferred between different cloud providers or between on-premises and the cloud via the **public internet**, making it vulnerable during transit if not properly encrypted and secured.
- Requires robust encryption and secure transmission protocols.

## Third-Party Vendors in the Cloud

### Expanded Scope
When using cloud services, you're dealing with more than just yourself and the cloud provider. You may also involve **third-party vendors** for:
- Infrastructure technologies (e.g., specialized network appliances, security tools).
- Cloud-based applications or services (e.g., CRM, HR software).

### Best Practices for Third-Party Security
1. **Ongoing Vendor Risk Assessments**: Regularly evaluate the security posture and practices of all third-party vendors as part of an overall **vendor risk management policy**.
2. **Incident Response Inclusion**: Ensure that third-party vendors are integrated into your **incident response plan** so everyone understands their role in case of a security incident.
3. **Constant Monitoring**: Continuously monitor third-party services and connections for any changes or unusual activity.

## Infrastructure as Code (IaC)

### Definition
**Infrastructure as Code (IaC)** is the practice of managing and provisioning computing infrastructure (like networks, virtual machines, load balancers, and applications) using machine-readable definition files instead of physical hardware configuration or interactive tools.

### How it Works
You define servers, networks, and applications *as code* (e.g., using YAML, JSON, or domain-specific languages).

### Benefits
- **Modification and Versioning**: Consistently create perfect versions based on the code.
- **Reproducibility**: Ensure consistency across environments.
- **Version Control**: Simplify tracking changes and rollbacks.
- **Automation**: Streamline deployment processes.
- **Disaster Recovery**: Facilitate recovery through code-based infrastructure definitions.

## Serverless Architecture

### Definition
**Serverless Architecture** is a cloud execution model where the cloud provider dynamically manages the allocation and provisioning of servers. A key component is **Function as a Service (FaaS)**, which involves applications broken down into individual, autonomous functions.

### Key Characteristics
- **No OS Management**: The cloud provider handles all OS security and maintenance.
- **Developer Focus**: Developers focus on server-side logic without worrying about the underlying infrastructure.
- **Stateless Compute Containers**: Functions typically run in stateless, ephemeral compute containers.
- **Event-Triggered & Ephemeral**: Functions are triggered by events (e.g., API calls, file uploads) and only run when needed, saving resources and costs.

## Microservices and APIs

### Monolithic Applications
- **Structure**: One large application handling all functionalities (user interface, business logic, data input/output).
- **Challenges**:
  - **Large Codebase**: Difficult to manage, debug, and update.
  - **Change Control**: A small change requires redeploying the entire application.
  - **Scalability**: If one part is under heavy load, the entire application scales.
  - **Resilience**: Bugs in one part can bring down the whole application.

### Microservice Architecture
- **Structure**: An application broken down into small, independent services (microservices) each running in its own process and communicating through APIs.
- **APIs**: Act as the "glue" that allows different microservices to communicate and work together.

### Benefits of Microservices
- **Scalability**: Independently scale individual microservices based on demand.
- **Resilience**: Outages are contained, so if one fails, others can continue functioning.
- **Security and Compliance**: Easier to apply security policies and compliance measures specifically to each service.
- **Agility**: Easier to develop, deploy, and update individual services without affecting the entire application.
- **Technology Diversity**: Different microservices can use different programming languages and technologies.

# Exam Takeaways

1. **Shared Responsibility Model**: Understand the concept of shared responsibility in cloud security. Be able to differentiate between customer and provider responsibilities for IaaS, PaaS, and SaaS across various components (data, applications, OS, network, physical infrastructure). Know that On-Prem is 100% customer responsibility.
2. **Hybrid Cloud Challenges**: Recognize the complexity introduced by hybrid clouds. Be prepared to explain specific challenges like network protection mismatches (authentication, firewall, server settings), diverse security monitoring logs, and increased data leakage risks due to public internet transfers.
3. **Third-Party Risk Management**: Understand that cloud environments often involve multiple vendors. Emphasize ongoing vendor risk assessments, integrating third parties into incident response plans, and constant monitoring to manage extended security boundaries.
4. **Infrastructure as Code (IaC)**: Define IaC and articulate its benefits for consistency, reproducibility, version control, automation, and simplified disaster recovery through code-based infrastructure definitions.
5. **Serverless Architecture (FaaS)**: Define Serverless/FaaS and its key characteristics. Understand that it removes the burden of OS management from customers, relies on event-triggered, ephemeral functions in stateless containers, and is largely managed by the cloud provider. Know its cost-saving and efficiency benefits.
6. **Microservices vs. Monolithic**: Be able to contrast monolithic applications with microservice architecture. Explain the role of APIs in microservices. Detail the significant advantages of microservices in terms of scalability, resilience, and granular security/compliance compared to monolithic applications.
